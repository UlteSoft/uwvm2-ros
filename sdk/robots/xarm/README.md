# UFACTORY xArm RobotMsg: complete telemetry source family

This directory is one concrete source increment for the UFACTORY backlog. It contains actual immutable upstream RobotMsg/Header/time source, two unbound complete catalogs, six runnable Guest-language source examples, a real native full-value codec oracle and an explicitly gated independent fixture publisher. It has not been generated, compiled, executed, connected to a robot or qualified for native ROS delivery. Java and C# are excluded. The other 19-vendor requirements and the remaining xArm interfaces/models remain required; see `remaining-work.json`.

The default authority is empty. The source never grants access merely because the vendor is UFACTORY or a record is named RobotMsg. The native publisher only emits a synthetic telemetry fixture on `/uwvm_xarm_fixture/robot_msg`; it never starts an xArm driver, sends motion, selects a controller IP, creates a service client or issues an emergency-stop command. State/mode/error values in telemetry are data, not executable instructions or safety evidence.

## Full schema and deliberate bounds

RobotMsg contains eleven top-level fields: Header; `state`, `mode`, `cmdnum`, `mt_brake`, `mt_able`, `err`, `warn` (all int16); dynamic float32 `angle`; fixed float32[6] `pose`; fixed float32[6] `offset`. No status scalar, frame metadata, angle, pose coordinate or offset coordinate is projected away. The fixed arrays retain their original declaration and length. No wrapper encodes a native struct or guesses an offset.

The only additional canonical limits are UTF-8 Header `frame_id` at most128 bytes and dynamic `angle` at most7 values. These bounds are explicit catalog input and part of the actual future canonical codec identity. They do not rewrite the upstream `.msg`, add a native sequence bound, infer a robot DOF or silently clip data. A value above the selected bound is refused. If a real selected model/source needs a different finite bound, it needs a separately reviewed catalog and actual regeneration; the present fixture cannot certify that model.

The catalogs use existing `uwvm-ros-official-standard-bounded-v1`. ROS1 includes complete std_msgs/Header with `seq`, native unsigned `stamp.sec`/`stamp.nsec` and `frame_id`. ROS1 time is the genuine native primitive; no fake Time.msg or MD5 is provided. ROS2 includes complete Header plus the complete signed-second `builtin_interfaces/msg/Time` definition and has no Header `seq`. Header and ROS2 Time are dependency-only (`registered:false`); only the intended RobotMsg is registered. Every transitive Message file is contained under its catalog root, with original bytes and exact origin association. No native identities are prefilled.

The original drivers set `angle` size from their actual configured DOF and publish the remaining fields from reports. The pinned ROS1 driver advertises relative `xarm_states`, while the pinned ROS2 driver advertises relative `robot_states`. Those are version-specific source facts, not grants or final absolute resources. Namespaces, remaps, report_type, robot/controller/firmware selection and actual dynamic values remain separate prerequisites. The independent fixture uses a dedicated isolated resource rather than assuming either real driver topic.

## Six actual Guest SDK applications

See `examples/robot_msg/recipe.json` and its English lesson notes. The six concrete applications are C, C++, Rust, JavaScript, AssemblyScript and TinyGo. They consume actual generated complete RobotMsg records/codecs and the current real SDK. C/C++/Rust reuse the unchanged reviewed generic vendor telemetry components; JS uses the actual embedded-Guest Session/CopiedTransport, AS the actual selected NativeApi, and TinyGo the actual SDK Session/Capability. None supplies a codec stub, native hash, manual ABI body or Host substitute.

A separately built fresh instance is required for each backend and mode. Mode0 is the default: ABI1 must succeed, actual open must return13 with no acquired handle, delivered count must be zero and all cleanup must succeed. Idle11, unsupported95, malformed22 or disconnected107 do not count as default denial. Mode1 is explicit and requires only one actual topic.subscribe alias, `xarm-robot-msg`, bound by the owner to the actual selected type/native identity/complete canonical identity/bound/resource/QoS. There is no topic.publish/service/action permission.

For mode1 each actual `R` byte on checked basic stdin releases exactly one poll, at most64. Idle11 consumes a caller credit. No timer, background thread/goroutine, automatic retry, reopen or buffer growth is introduced. A complete decoded fixture is checked field by field, then all actual owners are closed before a marker is written. External Runtime/Gateway/process ownership must still clean up a trap or kill; Guest source cannot promise cleanup after it stops executing.

The synthetic fixture checks all scalars, all seven angles and all twelve fixed-array values, plus complete Header/time. Binary fractions are exactly representable in float32, so comparison uses exact equality. Its Header is frame_id `xarm-base`; ROS1 seq19/sec42/nsec300000000, ROS2 sec-2/nanosec300000000. Scalars are state4/mode0/cmdnum3/mt_brake85/mt_able42/err7/warn9. The source fixture values are not observations of a real robot, not commands and not a claim that these combinations are valid controller states.

## Independent native oracle and fixture endpoint

`native/roundtrip.cc` includes the actual newly native-bound `native_ros1.hpp` or `native_ros2.hpp`, real installed xarm_msgs type and complete Header/Time. It compares actual installed native identity to the original exported identity, exercises full-value encode/decode, trailing/truncated input, over-bound angles, over-bound frame_id, nonfinite float32 and invalid nanoseconds with transactional output/destination checks. Empty dynamic angles remain schema-valid without applying unrelated JointState equal-length semantics. It creates no ROS entity or robot connection. A codec-only pass cannot prove native delivery.

`native/publisher.cc --publish-fixture` is a real independent ROS1/ROS2 publisher source. It first stops for an external retained-pidfd map/ELF/library proof, consumes `I`, verifies actual native identities and complete codec acceptance, then creates exactly one publisher on `/uwvm_xarm_fixture/robot_msg`. Caller `M` credits allow at most64 checks for exactly one independently owned Gateway subscription. After a matched marker the owner supplies `P`; only then is the full synthetic fixture enqueued once. The marker explicitly reports `delivery_qualified=0`. The process waits for `F` so the external owner can retain independent Guest all-field evidence before teardown. Every wait and process/thread/resource remains bounded by the external native owner; this source is not a new process controller. EOF/wrong gate, extra/missing subscriber or any exception fails. ROS2 explicitly selects domain205/reliable/volatile/keep-last1 for this isolated fixture; ROS1 is unlatched queue1. The native fixture is not the original robot driver's topic implementation.

`native/CMakeLists.txt` declares actual native roundtrip/publisher targets with full MD requests, link trace and selected real catkin/ament/xarm_msgs/standard packages. It performs no download, generation, test registration or execution. Root must bind actual compiler/sysroot/SDK/CMake configure/build command identities and verify real effective MD/MT/input/ELF/link/map evidence; requested flags alone are not consumption proof. The concrete ROS2 native oracle targets the selected Jazzy family with actual RIHS01 support. Older introspection-only ROS2 is separate explicit source/SDK work, never an automatic fallback.

Acceptance needs real current source/model/artifact matching, actual installed native identities/capacities, actual bound complete generation, actual target binaries/imports, strict loaded-map FD/hash proof, actual Gateway registration, independent publisher enqueue, Guest full-field receipt, default-denied proof, original64/swap-zero resource and complete root preservation, and normal owner cleanup. Markers/counters/source peer/code generation/compilation alone prove none of that. No such acceptance has run here.
