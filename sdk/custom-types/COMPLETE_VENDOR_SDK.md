## Start at the raw import boundary

Read `sdk/include/roswasm/abi/ros1.h` or `abi/ros2.h` and the corresponding
`roswasm/ros1.h` or `roswasm/ros2.h`. The actual vendor kit links a raw denied
example and then a typed application. Compile with the genuine selected Wasm
producer, inspect actual full imports and invoke through uwvm2. Begin with no
ROS grants: a capability open must refuse13 without publishing a handle. The
base standard input/output/error exception is independent of ROS authority.

For a positive run the operator supplies each exact module, backend, alias,
operation, resource/type/Native/canonical identity, QoS and finite resource limit.
The SDK cannot generate grants, enable DDS, discover credentials, acquire a
robot lease, open native sockets or configure debug/update/policy management.
The controlled Native Gateway remains outside the Wasm sandbox. Its SDK/process
permissions and robot-side safety supervisor must be owned explicitly.

## Keep one coherent generated domain

Every record, RPC facade, metadata proof and Native adapter used in a physical
generated build belongs to one complete catalog. Shared C guards, Native-name
symbols and canonical capacities are deliberate. Do not concatenate independent
generated headers. For several vendors in one typed domain, explicitly merge
and deduplicate their complete compatible declarations and regenerate once
within the admitted limits; no tool silently unions authorities or inventories.
Alternatively compile separate Wasm libraries with their own complete SDK
domains and use the Runtime's explicit multi-module/preload ABI to exchange
copied application values. Permissions remain separately bound to each actual
module and ROS backend. A library call does not grant its caller new rights.
The complete generator selects one ROS backend per catalog; dual-backend
applications must retain that separation. See the project's multi-module and
ROS permission documentation for the actual command syntax.
