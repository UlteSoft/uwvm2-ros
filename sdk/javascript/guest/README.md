# JavaScript inside an actual Wasm guest

This embedding compiles the pinned official QuickJS interpreter, immutable
JavaScript modules, copied C bindings and application into **one wasm32 Wasm
principal**. Application code, service handlers, Promise continuations and
local callbacks execute inside that principal. Each preloaded JavaScript
library has its own interpreter, memory and lifetime. The existing external
Node bridge and relay remain separate supported integration paths; their tests
do not establish execution of JavaScript inside Wasm.

The implementation is source-prepared. A preparation report, source model or
Node fake is not a compiled-engine, Runtime, native ROS, simulator or performance
result. Retain the actual validation and execution evidence described below
before qualifying a particular artifact/toolchain/backend combination.

## Start with a complete, bounded application

Read [the progressive guest examples](../../examples/javascript_guest/README.md)
in order. Their exported `main()` returns integer zero after checked cleanup.
It may return a Promise resolving to zero; the engine executes only a finite
number of guest jobs. No Node process, `WebAssembly.Memory` facade, socket,
filesystem loader, environment, clock or native ROS client library is used.

For an application, import `createGuestSession()` or
`createAsyncGuestSession()` from `sdk/javascript/guest.mjs`. These construct the
existing synchronous or asynchronous SDK over `CopiedTransport`. Both paths
reuse the existing resource validation, canonical codecs, ownership, polling,
services, Actions, parameters, graph, TF, lifecycle and event implementations.
The transport changes byte storage; it does not introduce a second ROS API.
See the [API guide](../API.md) for the exact supported operations and limits.

The embedded builtin `roswasm:guest_native` is provided by C **inside the same
Wasm**. `describe()` returns its selected ABI and C-owned scratch layout.
`invoke(index, arguments, input, slotSeed, snapshotLength)` independently checks
every exact Number/BigInt scalar, real Uint8Array, memory-zero range, arity and
scratch capacity before entering the original ROS import. It makes one bounded
copy in each direction and returns an owned result. No pointer or JS object is
sent to the Gateway. Constructing a transport object in an external host is not
an identity proof; actual artifact and Runtime observations are required.

ROS1 retains all 38 ABI-v1 imports; ROS2 retains all 43. The dispatcher and form
table come from the existing `relay_protocol.h`, while declarations come from
the actual C ABI headers. BigInt is mandatory for i64 values even on wasm32.
Codecs use guest-local UTF-8 with strict decoding and literal BOM preservation.
`TextEncoder`, `TextDecoder`, BigInt, typed arrays and Promises are available.
Streaming TextDecoder is deliberately refused; SDK records are complete bounded
frames. Math.random uses an explicit deterministic artifact seed, not entropy.

## Closed source and finite execution

`recipes.json` contains 30 explicit build selections: the original28 plus a
floating-scalar provider and its actual import consumer. Each expands to a closed
manifest with exact module IDs/source paths, scalar imports/exports, backend,
memory bounds and engine limits. The producer embeds UTF-8 **source bytes**;
it never executes a host `qjsc`, generated bytecode, user JavaScript or a compiler.
Only listed modules and the small declared `roswasm:` builtins can resolve.
Relative imports normalize within that table. Absolute paths, escape paths,
native `.so` loading, `std`, `os`, Node modules, unknown modules and import
attributes have no fallback. Dynamic import obeys the same closed table.

The custom QuickJS allocator counts requested bytes plus its aligned ownership
prefix. Heap, JS stack, source bytes, module count, total Promise jobs and
interrupt polls have explicit finite limits. The Wasm maximum and the owner's
RSS/cgroup guards additionally bound allocator overhead and nonengine memory.
`limits.stack_bytes` reserves the actual low-address Wasm C stack and is
unchanged by the JavaScript evaluation policy. QuickJS receives a separate,
nonzero evaluation budget of exactly half that reservation. A function frame
already lies below the reservation's upper end: subtracting the whole reserved
size from it would wrap QuickJS's unsigned stack limit below address zero.
Every engine entry refreshes its current top only after checking a practical
16-KiB C-call headroom; insufficient room produces sticky LIMIT3. The first
runtime creation applies the same check and refresh. QuickJS's own active
stack checks, the Wasm stack reservation and the owner's limits all remain in
force. This headroom is a bounded policy, not a proof of every compiler frame;
actual initialization and deliberate recursive-overflow refusal require real
Runtime tests. No stack guard is set to zero and no memory maximum is raised.
An interrupt poll is not an instruction or time unit. The owner still enforces
an actual deadline, particularly around a blocking admitted ROS operation or
the explicit basic-stdin gate. The engine creates no background thread or timer.

The three reviewed release adaptations disable OS atomics, avoid a platform
allocation-size helper and replace time-based PRNG initialization with the
explicit seed. An unused dtoa `setjmp.h` include is removed only after an exact
source check confirms no nonlocal-jump operation. `quickjs-libc.c`, `qjs.c`,
`qjsc.c`, OS modules and native dynamic loaders are not compiled. Upstream
source/license bytes remain pinned in `upstream-lock.json`; the producer copies
them before recording these narrow adaptations. The official
[release](https://bellard.org/quickjs/) and
[embedding documentation](https://bellard.org/quickjs/quickjs.html) describe the
engine; this embedding supplies the restricted loader and lifecycle.

## Prepare explicit serial build jobs

Acquire the exact official release as a separately audited input. The lock
requires `quickjs-2026-06-04.tar.xz`, 621500 bytes, SHA256
`b376e839b322978313d929fd20663b11ba58b75df5a46c126dd19ea2fa70ad2a`.
It checks every retained engine source/header used by this build. Do not replace
the release with a moving Git branch or build a package fetched by a JS import.

Every path below is an **explicit owner-selected absolute input**, not a PATH
lookup or an example permission grant. Run preparation and every later job
inside the owner's exact current 64GiB/swap-zero cgroup with one job at a time.
Use a fresh owned output outside all frozen source/tool trees. Local testing
and products belong under `/tmp`; remote storage is selected by the owner.

```sh
python3 -B "$FROZEN_SOURCE/sdk/javascript/guest/prepare.py" \
  --source-root "$FROZEN_SOURCE" --quickjs "$PINNED_QUICKJS_SOURCE" \
  --manifest "$FROZEN_SOURCE/sdk/javascript/guest/recipes.json" \
  --variant 00-raw-ros2 --out "$FRESH_OWNED_OUTPUT" \
  --clang "$PINNED_WASI_CLANG" --linker "$PINNED_WASM_LD_ALIAS" \
  --sysroot "$PINNED_WASI_SYSROOT" \
  --resource-dir "$MATCHING_CLANG_RESOURCE_DIR" \
  --libc "$PINNED_WASIP1_LIBC" --libm "$PINNED_WASIP1_LIBM" \
  --printscan "$PINNED_WASIP1_FULL_FORMAT_ARCHIVE" \
  --builtins "$MATCHING_WASIP1_BUILTINS" --validator "$PINNED_WASM_TOOLS"
```

The selected clang resource directory and builtins must belong to the actual
selected package. In particular, WASI SDK33's clang22 resources are distinct
from a host clang23 installation. A host archive is not a Wasm archive. No
package installation, compiler, subprocess or validator is started by this
producer. It writes `module_table.c`, `scalar_trampolines.c`, exact source/tool
pins, allowed-symbols file and `report.json` with status
`PREPARED_NOT_COMPILED`. The report's ordered argv jobs compile one C source at
a time, link with the explicitly selected WASI archives and validate the result.
Execute them through the existing guarded serial runner, preserving each job's
stdout/stderr, exit status, full `-MD` include closure and linker `--trace`.
The producer admits bounded regular inputs before body allocation, opens them
with `O_NOFOLLOW` and compares descriptor/path/stat identities after reading.
Source bytes have per-file and remaining-total limits. The explicit linker
alias preserves the `wasm-ld` basename even when its physical target is a
multicall `lld`; both alias selection and physical file hash are retained.
The alias is passed as `-fuse-ld=/absolute/path/wasm-ld`, which the
[LLVM22 WebAssembly driver](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.0/clang/lib/Driver/ToolChains/WebAssembly.cpp)
uses to select the executable. Its Wasm driver does not consume `--ld-path`.
The four pinned archives are ordinary direct linker inputs: the
[Wasm LLD archive reader](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.0/lld/wasm/Driver.cpp)
admits their members lazily. ELF `--start-group` and `--end-group` are not
accepted by this Wasm linker and are not emitted.
Link jobs use `--threads=1`; compile jobs use `-UNDEBUG` and exact `-MT` object
targets with full dependency files. No implicit linker PATH lookup is required.

`--printscan` must select the actual matching sysroot's nonthread
`lib/wasm32-wasip1/libc-printscan-long-double.a`, physically pinned like libc,
libm and compiler builtins. Place this official full numeric formatter before
libc. WASI libc's default formatter retains a long-double refusal diagnostic
that references stderr and its general file backend, including close/seek,
even when the engine only needs memory formatting. The official full-format
variant removes that diagnostic dependency while retaining the original
numeric-formatting algorithms. See its [build selection](https://github.com/WebAssembly/wasi-libc/blob/main/libc-top-half/CMakeLists.txt)
and [diagnostic source](https://github.com/WebAssembly/wasi-libc/blob/main/libc-top-half/headers/private/printscan.h).
Those links explain the dependency; the selected physical archive's actual
hash, whole tool-package inventory and retained linker trace decide the build.
Do not replace libc functions with fabricated success, omit assertions, or add
WASI imports to make an inspection pass. Actual pure reactors must still have
zero WASI imports; command variants keep exactly fd_read/fd_write/proc_exit.

The owner must keep at least 4GiB memory reserve and 8GiB disk reserve on the
output **and backing ancestor filesystems**, reject input/output overlap, bind
current boot/cgroup/device/inode/CPU/memory/swap identities, forbid escape or
cgroup migration, supervise every descendant and retain owned pidfd cleanup.
All ancestor OOM counters must remain unchanged. A child cannot be admitted
outside the guard merely because preparation itself starts no children.

## Binary and runtime qualification

For **every** selected variant, reopen and hash the final artifact, run actual
Wasm validation and independently inspect exact module/name/signature imports,
exports, memory limits and absence of a start section. Check against the
manifest and public ABI, not just the producer's expectation or Wasm magic.
There must be no `env.*`, unsupported WASI, unknown module, native allocator,
time, randomness, thread, file, environment or socket import. Inspect library
imports and all scalar trampoline exports, including i64 vs i32 widths.

The command flavor imports the selected complete ROS ABI plus basic WASIp1
`fd_read`, `fd_write`, `proc_exit`. It has no Wasm start section: the Runtime
calls its exported `_start` normally. Import presence confers **no ROS grant**.
Run the raw and complete-denied lessons with empty ROS permissions, exact
protected refusal bytes and an independent no-native-effect witness. Positive
Node, service, Action, custom-type and event cases require separate narrowly
configured aliases/type identities/quotas and independent native observations.
Never use a default positive alias plan or count an empty application plan as
native resource coverage.

Pure `reactor-vision`, `reactor-callback` and `reactor-motion` recipe variants use
backend zero, compile neither `native_ros.c` nor `stdio.c`, and allow **zero ROS
and zero WASI imports**. Motion's only external scalar import is the configured
`callbacks.on_motion`. Do not silently grant a new import to make a build pass.
The benchmark command currently retains the selected ROS dispatcher even
though its kernel makes no ROS call; it is not labeled a zero-ROS-import root.

`acceptance.json` enumerates the exact 30 variant IDs and required observations.
Limit fixtures first write `JS_GUEST_LIMIT_ARMED\n`, then deliberately exceed
one selected budget. Require lifecycle LIMIT and actual process exit3 within
the external deadline; a compiler failure, startup OOM, arbitrary trap, timeout
or missing armed marker is not that positive refusal result. Source models
check recipes and boundaries only; they cannot satisfy these runtime gates.

## Reactor and callback lifecycle

A pure library exports `roswasm_js_init`, `roswasm_js_pump`,
`roswasm_js_status`, `roswasm_js_close` plus the configured scalar functions.
Local status values are OK0, PENDING1, EXCEPTION2, LIMIT3, BUSY4, CLOSED5,
INVALID6; they are **not ROS errno**. `init` evaluates bootstrap and the closed
entry. Pump takes an explicit bounded job budget. Pending work is not success;
the caller must observe OK before treating initialization as complete. There is
no implicit `_initialize` or native event loop. Every admitted top-level call
has an interrupt bound; total job usage is finite for the instance lifetime.

Each scalar export names an existing JS function, exact core scalar types, explicit
failure scalar and whether its first call may initialize the engine. Arguments
and return values are independently checked by C. A JS error poisons engine
status; a failure scalar cannot erase it. Check status after calls where that
distinction matters. No shared pointer, JS object, C++ object, ROS handle or
function pointer crosses modules. Guest JS motion calls a real scalar Wasm
callback import; the callback's JS registry lives in the owning Wasm instance.
Application generation tokens are lifecycle bookkeeping, not Runtime identity.

Supported scalar types are `i32`, `u32`, `i64`, `u64`, `f32`, `f64`. Signed and
unsigned forms share their Wasm integer value type but retain strict local
range checks; i64 forms require BigInt. Floating forms accept Number only,
preserve Infinity/NaN class/negative zero and use actual f32 demotion where
selected. NaN payload bits are not promised. Manifest failure scalars must be
explicit and finite; runtime status independently records failure. These core
FFI rules leave finite ROS-message codec checks unchanged. `float_guest` and
`10-floating-modules` exercise real separately instantiated f32/f64 providers,
including rounding, overflow and rejected implicit coercions.

Close application-owned ROS resources explicitly **before** closing the engine.
GC never closes Runtime capabilities. `close` rejects reentrancy, discards
remaining jobs and destroys the context/runtime; use of a closed scalar library
returns its explicit failure value with CLOSED status. Root's process ownership
and cleanup still apply after a trap or abort, when guest cleanup cannot run.

## Pinned typed-array C API arguments

The QuickJS 2026-06-04 `JS_NewTypedArray` entry point forwards the C argument
vector to a constructor that reads three argument slots without adding
`undefined` values. All embedding calls therefore provide a real three-slot
vector: explicit zero length for the initial empty class probe, or the copied
ArrayBuffer plus two `JS_UNDEFINED` optional arguments for byte results.
This preserves ordinary `new Uint8Array(buffer)` behavior and buffer ownership.
Passing `argc=1` with only one C slot can instead read unrelated stack values
as the offset/length; passing a null vector for an empty array is also invalid
for this pinned implementation. The unchanged release source is retained as
an input; the correction belongs to our C embedding. See the
[upstream report](https://github.com/bellard/quickjs/issues/526).

The actual raw ROS1 example exposed this as `invalid length` in
`TextEncoder.encode('ungranted')`. Its failed run remains separate evidence;
source correction alone does not qualify the rebuilt examples or their ROS IO.
