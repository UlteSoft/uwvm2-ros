# UWVM2 ROS Runtime Extension architecture

The runtime binary contains two independent builtin imports, `uwvm_ros1_v1` and `uwvm_ros2_v1`. Each backend connects to its own independently compiled Linux Gateway through a private Unix socket. uwvm2 remains C++26 and has no ROS library dependency. Noetic runs in Ubuntu 20.04 userspace and Jazzy in Ubuntu 24.04 userspace.

Directly loading roscpp and rclcpp in one process was not chosen: Noetic and Jazzy have different supported userspaces, libc and C++ library deployment expectations; ROS1 initialization and ROS2 contexts/RMW have different lifetimes; inherited environment/remapping can affect identity; executor callbacks and failures would share the worker address space. Separate processes permit independent library versions, thread pools, lifecycle and crash isolation. There is no automatic ros1_bridge or ROS-version fallback.

The main trust boundary is Guest → trusted Runtime/capability host → authenticated IPC → trusted ROS Gateway → ROS network. Native plugins execute arbitrary trusted host code and are part of the trusted computing base; WASI cannot sandbox their C++ execution. This implementation refuses additional native plugins in an enabled strict ROS worker.

The Gateway loads an authoritative, owned regular policy file that is not writable by group or others into an immutable in-memory policy snapshot. The worker authenticates its UID with SO_PEERCRED; the Gateway authenticates the worker UID and exact PID. Every Instance/backend uses a separate connection. A randomly issued session identity is tied to that connection, and requests cannot select another Instance. Before any resource operation, `session.bind` must exactly match the complete sorted backend network identity and capability manifest. Scope/group names do not establish network principals. Every operation is authorized again in the Gateway.

A Group shares only an immutable policy description. Instance identity comes from the actual runtime instance pointer, runtime generation and trusted Runtime module record. Guest module-name strings and native plugin names never select that identity. Cross-module call ancestry is marked in trusted thread-local runtime frames, including tail-frame replacement. The ROS identity query rejects cross-module ancestry because no delegation mechanism has been authorized or implemented.

The interpreter and native LLVM full-compilation paths have separate caller-authentication contracts. LLVM ROS execution requires actual LLVM translation, full compilation and generated instruction call-stack frames, including trusted function-boundary and tail-call ancestry handling. A debugger-enabled label alone does not establish that contract; unsupported execution configurations fail before ROS Guest startup. Actual execution qualification remains specific to each backend, source manifest and target architecture.

Runtime updates and debugger configuration are trusted host management operations. They are absent from the ROS Guest ABI. A successful function replacement retires the affected module's complete ROS authority before publishing its new entry, then drains its Host state while execution remains paused. Reset drains execution before cleaning old-epoch ROS state and retiring module storage. The [security lifecycle](security.md#trusted-updates-and-debugger-lifecycle) describes the permission and debugger-reference transitions.

ROS callbacks remain in the Gateway executor and copy validated messages into bounded queues. Guest code polls events synchronously using copy-safe controlled memory APIs with 64-bit offsets and explicit memory indices. A ROS callback never enters Wasm or keeps a Guest pointer. Closing/revoking authority drains related resources and events. Connection loss retires the session and its native resources; reopening requires the current immutable policy and cannot reopen revoked aliases.

The detailed protocol is in [ipc.md](ipc.md), Guest layouts in [abi.md](abi.md), target semantics in [multimodule.md](multimodule.md), and real execution evidence in the final test report. Unsupported adapters fail closed and do not return success.
