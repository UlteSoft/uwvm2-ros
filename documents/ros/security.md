# ROS capability security boundary

ROS1 and ROS2 are disabled by default, including when their import support is compiled in. Each version's initial Global target is disabled with no connection fields or capabilities; newly created Single and Group targets have the same empty, disabled state. Authority requires explicit CLI configuration: enable the selected target, supply its connection fields, and grant each permitted operation with every required limit. `enable` supplies no resource permission, and `grant` does not enable a target. A disabled target denies resource access even if it retains configured grants.

Capabilities are explicit single-operation grants on canonical resource names with trusted generated type identities and explicit semantic/resource limits. Enabled targets with missing fields fail validation. An unbound module uses its ROS version's Global target. An explicit Single or Group binding selects only that target, including its enabled state, connection fields and capabilities; a disabled or empty explicit target never falls back to Global authority. Explicit Global grants therefore apply only to unbound modules. ROS1, ROS2 and WASI namespaces do not imply membership or authority in one another.

A handle encodes a slot and generation, but it is valid only in the independently selected trusted runtime Instance table and ROS version. Slots never migrate between Instances. Closing a slot invalidates its generation; revocation invalidates every handle to the alias and refuses reopening. Native pointers are never returned to Guest code. Per-Instance/backend authorization leases serialize side effects with revocation using the same trusted lock. Independent backend locks avoid making one backend's blocked IPC request hold the other backend's authority lock.

Host checks occur at capability open, every resource operation, response/event delivery, close and revocation. They verify caller ancestry, live handle, operation, trusted type, canonical structure, byte quota, monotonic rate quota and resource state before a network side effect. Gateway policy checks repeat this process. Topics and service payloads use a documented bounded canonical wire format and are decoded into official generated message/service objects. ROS1 serialization bytes are not sent as ROS2 CDR.

The Gateway authenticates Linux peer credentials, uses private owned socket directories, refuses ambiguous framing, enforces monotonic request IDs, bounds frames before allocation, and requires an exact policy manifest before accessing ROS resources. A mismatched policy, type hash, backend or session cannot grant authority. The worker and Gateway are trusted; a process with authority to replace them or their owned configuration is outside the Guest boundary.

WASIp1 also starts without optional authority. Its initial configuration does not inherit the host environment, install directory or socket preopens, or grant optional clock, random or process capabilities. Standard input, output and error have only their basic directional, metadata and readiness rights; their inheriting rights are empty. A trusted CLI selection must grant each additional operation independently. Applicable Single/Group settings are resolved explicitly and ROS enable/grant options do not change WASIp1 configuration.

When any ROS target is enabled, the strict worker additionally refuses WASI socket/directory preopens and explicitly requested host environment inheritance for every loaded module whose WASIp1 support is enabled, including modules without ROS grants. Additional trusted native plugins and socket standard streams are also refused. Pipe/file standard streams and native execution remain host deployment responsibilities: use trusted launch control and an isolated worker network namespace when guaranteeing that Guest has no alternate network route. The runtime is not a general native C++ sandbox and does not enforce ACLs on unrelated external ROS1 nodes.

The existing CLI can load a trusted shared library while parsing its plugin option, before the mixed ROS/plugin startup guard runs. Native library initializers therefore remain part of the trusted computing base. The tested guard rejects Guest execution; it does not sandbox or roll back native initializer effects.

ROS1 has no equivalent of DDS Security. Its Master and topic peers must be confined by the deployment network boundary. ROS2 `disabled-test` explicitly disables network security; it cannot be described as a production security enclave. `enforce` needs externally supplied certificates and permissions and a supported RMW. The internal Wasm capability table still enforces Instance authority independently of DDS permissions.

Wasm signing, software publisher identity, production certificate generation and supply-chain authentication are outside this project. No permission levels, roles or templates exist.

## Trusted updates and debugger lifecycle

The ROS Guest import registries contain business operations only. They expose no Runtime update, debugger configuration, policy mutation or permission-grant operation. Management is performed through trusted native APIs and explicitly selected host debugger channels. The private debugger control descriptor is authenticated and sealed before Guest setup; its native descriptor number is not a WASI descriptor or a ROS capability. Guest standard-stream aliases of that endpoint are rejected, and WASI file admission checks the sealed endpoint independently.

A successful LLVM function replacement permanently retires ROS authority for the entire affected module in its current Runtime incarnation, including unchanged functions and a module which has not opened a ROS handle yet. The retirement flag is published before any replacement entry becomes visible. Rejected preparations and rejected commits do not retire live authority. Unaffected modules retain their independent policy and state.

While execution remains paused, trusted post-commit cleanup invalidates the affected handles, closes local Gateway sessions and discards queued, pending and reserved events and request identities before the controller acknowledges completion. Cleanup runs outside the stopped-domain/publication mutex and performs no RPC or Guest callback. The replacement receives no inherited grant, refreshed quota or automatically reopened alias. Using ROS again requires a fresh trusted launch with explicitly selected policy. Runtime reset first drains actual execution, then cleans the old ROS epoch, and only then retires its Runtime epoch and module storage.

The DAP adapter retires old frame and variable references before sending a replacement or management script, including an attempt whose reply fails or is uncertain. It accepts a new stop view only from a complete authoritative refresh. See the [real management integration contract](../../tests/ros_debugger/README.management-runtime.md) for the distinct native, private Control and DAP checks; implementation and authored tests alone are not execution evidence.

Unknown custom Service, Action and message types are rejected until a trusted generated adapter with concrete request, response and event validation exists. Standard supported adapters are listed in [capabilities.md](capabilities.md) and [abi.md](abi.md). A schema entry alone is not an implemented ROS API. Tests must inspect actual ROS side effects before claiming network authorization holds.

## Native network ingress boundary

The worker validates Guest memory ranges, canonical message structure, finite numeric fields, exact resource/type identities and explicit byte/rate limits before emitting IPC or native ROS effects. Gateway event/TF/ParameterEvent filters run before retaining or delivering bridge data. This bounds bridge-owned event queues and caches.

Generated roscpp/rclcpp callbacks run after their native serializers/RMW have received and deserialized input. Capability queue/message limits do not impose a hard ceiling on all transient allocations inside ROS/DDS middleware for hostile external packets. Native ROS/DDS libraries and the trusted launcher are TCB. SROS2 signed peer/resource permissions reduce the admitted network surface; the existing shared64GiB cgroup bounds the actual processes. Fully pre-deserialization rejection of malicious external ROS payload allocation is UNSUPPORTED by these typed callback adapters. It is not evidence that a Guest can bypass its prevalidated outbound IPC limits.

ROS framework discovery and node initialization are necessary network protocol behavior of the explicitly configured connection. They do not grant Guest Graph or Parameter APIs. Jazzy's internal `/parameter_events` subscription is listed explicitly in the test DDS policy; selected parameter values are delivered only by a separate exact-node/name capability. Untrusted native plugins have no Wasm sandbox guarantee; strict enabled ROS execution rejects additional native extensions.
