# ROS1 SDK and distribution compatibility

The Gateway selects public SDK features, not a ROS distribution threshold.
The maintained catkin path covers the development-SDK layouts used by Groovy,
Hydro, Indigo, Jade, Kinetic, Lunar, Melodic and Noetic. These are source
adaptation targets. A distribution/architecture is **not validated** until its
own frozen SDK, compiler, generated headers, Gateway and actual native behavior
have passed the selected acceptance lane. An earlier Noetic result does not
qualify another SDK, version, architecture or library ABI.

The Guest import backend remains ROS1. A distro selection never creates a
capability, loads an ambient ROS plugin, enables a debug service or grants
network access. Ordinary configuration retains the existing Gateway and seven
ROS1 native-probe targets. `UWVM_ROS1_BUILD_PROBES=OFF` is an explicit deployment
build option; such a build does not satisfy the full native-probe acceptance
inventory.

## Select the compiler and SDK explicitly

Use a modern CMake (at least 3.10), C++17 compiler and compatible target C++
library/sysroot. The older ROS distributions' default C++03/11/14 toolchains
do not implement this adapter's `optional`, `string_view`, inline variables and
integer `charconv`. Do not lower the language standard or copy an arbitrary
new `libstdc++.so` into an old userspace: its libc and target dependencies must
also match. A pinned rebuilt ROS SDK on a newer userspace is another supported
selection mechanism, distinct from building against stock historical binaries.
`UWVM_ROS1_CXX_STANDARD=17` is the default. A caller may select 20 or 23 only
when both that SDK's generated headers and the target library pass the same
contracts (CMake >=3.12 for C++20, >=3.20 for C++23). A higher language setting
does not imply compatibility with an older generator's C++ output.

For an installed catkin SDK, select its prefix/toolchain before configuration:

```sh
mkdir -p /absolute/owned/build-ros1
cd /absolute/owned/build-ros1
cmake /absolute/uwvm2-ros/gateways/ros1 \
  -DCMAKE_PREFIX_PATH=/absolute/selected/ros-sdk \
  -DCMAKE_TOOLCHAIN_FILE=/absolute/selected/target-toolchain.cmake \
  -DUWVM_ROS1_DISCOVERY=CATKIN \
  -DUWVM_ROS1_CXX11_ABI=auto
cmake --build . -- -j1
```

The toolchain file must specify the target compiler/sysroot and any required
target runtime/linker paths. Configuration **compiles and links** small
contracts without `try_run` or target execution, so cross builds do not require
binfmt/QEMU. The `ros::init`/`NodeHandle` string-bearing link checks retain the
compiler's default libstdc++ ABI when it works. If it fails, `auto` chooses ABI
0 or 1 only when exactly one of those actual links succeeds. An explicit
`-DUWVM_ROS1_CXX11_ABI=0` or `=1` must pass the same link check. A link result
does not prove that the selected runtime libraries will load or behave
correctly in the final rootfs; that remains an actual lane obligation.
`CMakeCache.txt` exposes `UWVM_ROS1_SELECTED_CXX11_ABI=0|1`, established by
compile-time target-header checks, so independently compiled native fixtures
can carry the same bit. For a genuinely non-libstdc++ SDK it records
`NOT_LIBSTDCXX`; such a fixture omits the GCC-specific definition and must use
the same target compiler/library. The value is not inferred from host GCC or
the ROS distribution label.
The example uses a Makefiles/Ninja generator's serial `-j1` argument, including
with CMake 3.10; select the equivalent serial flag for another build tool.

Successful configuration writes `uwvm_ros1_features.json` with closed fields
`format_version`, `backend`, `cxx_standard`, and boolean `features`. It records
the checked library/API capabilities and whether legacy TF spelling or a
standard-service backport was selected. It is removed before reconfiguration
and published only after all required compile/link probes succeed. It is
metadata for the external matrix, never a native execution receipt.

The selected ROS SDK may use Python 2 while the repository's host acceptance
tools use modern Python 3. They are separate interpreters. No tool changes the
SDK's Python shebangs or automatically chooses a runtime permission for either.

## Standard-service backports

Early SDK snapshots have `std_srvs/Empty` but no Trigger and/or SetBool. If a
native standard-service header exists in the selected include directories it
always wins. Only a missing service is generated into the build directory from
the exact official definition under `compat/std_srvs`, with package name
`std_srvs`, by the selected SDK's own `gencpp` and templates. Request/response
types, serializers and service traits are generated by ROS, not emulated by the
Gateway. The official type and MD5 strings are checked before compilation.
This adds no native library and grants no service operation.

In catkin mode CMake can locate `gencpp`. Override these host paths explicitly
when the SDK requires its own generator environment, especially Python 2:

```text
-DUWVM_ROS1_GENERATOR_PYTHON=/absolute/host/python-for-selected-ros-sdk
-DUWVM_ROS1_GENCPP_SCRIPT=/absolute/selected/sdk/gencpp/gen_cpp.py
-DUWVM_ROS1_GENCPP_TEMPLATE_DIR=/absolute/selected/sdk/gencpp/templates
```

Generation uses `PYTHONDONTWRITEBYTECODE=1` and `-B`, has a 120-second bound,
and writes headers/logs only under the build directory. The caller supplies
the correct generator-module environment; CMake does not source an ambient
setup script. Every generated header, template/interpreter/tool input and SDK
must be retained/pinned by the actual build lane. Generation success is not a
native service execution result.

## XML-RPC, TF and legacy discovery

`compat.h` accepts either the public flat xmlrpcpp headers found in early SDKs
or the later `xmlrpcpp/` layout. It retains the existing bounded nonblocking
XML-RPC client, parser limits and operation deadline. `tf_compat.h` selects the
actually linkable `tf2_ros::Buffer` or Groovy's `tf2::Buffer`; both are always
constructed with `debug=false`. In particular, Groovy's default `debug=true`
must not advertise `view_frames` as a side effect of creating a permitted cache.

For a maintained SDK without catkin package discovery, use the explicit path:

```text
-DUWVM_ROS1_DISCOVERY=EXPLICIT
-DUWVM_ROS1_INCLUDE_DIRS=/absolute/sdk/include;/absolute/overlay/include
-DUWVM_ROS1_LIBRARIES=/absolute/sdk/lib/libroscpp.so;...
```

Quote semicolon lists in an actual shell. Both lists are required and every
entry must exist and be absolute. Supply all dependency libraries and official
generated message headers, including tf2/TFMessage and Fibonacci Action.
Missing standard services also require the explicit host generator paths above.
All the same public API, string ABI and TF compile/link checks apply. This is a
real build entry for an explicitly maintained pre-catkin SDK/official overlay;
it is not a claim that an unmodified Fuerte, Electric or earlier installation
already contains the required tf2/interfaces. A missing required public API
fails configuration explicitly instead of silently removing a feature.

The process-security platform contract is separate from the ROS distro. Old
ROS userlands can run on a current Linux host/container with the required
pidfd/peer-credential facilities and a suitable target libc. This compatibility
layer does not replace pidfds with numeric-PID signalling, weaken entropy or
claim support for an old kernel that lacks the security primitives.

## Primary sources and verification boundaries

* [REP 3 target platforms and language baselines](https://www.ros.org/reps/rep-0003.html).
* [GCC libstdc++ dual ABI](https://gcc.gnu.org/onlinedocs/libstdc++/manual/using_dual_abi.html).
* [Indigo xmlrpcpp flat-header installation](https://github.com/ros/ros_comm/blob/indigo-devel/utilities/xmlrpcpp/CMakeLists.txt).
* [Groovy TF Buffer namespace and debug argument](https://github.com/ros/geometry2/blob/groovy-devel/tf2_ros/include/tf2_ros/buffer.h).
* [Groovy gencpp service-generation entry](https://github.com/ros/gencpp/blob/groovy-devel/scripts/gen_cpp.py)
  and [genmsg service/request/response generation](https://github.com/ros/genmsg/blob/groovy-devel/src/genmsg/template_tools.py).
* [Official Trigger definition](https://github.com/ros/ros_comm_msgs/blob/noetic-devel/std_srvs/srv/Trigger.srv),
  [SetBool definition](https://github.com/ros/ros_comm_msgs/blob/noetic-devel/std_srvs/srv/SetBool.srv)
  and [their introduction history](https://github.com/ros/ros_comm_msgs/blob/indigo-devel/std_srvs/CHANGELOG.rst).

This change is source-only until the root-controlled build and behavior lanes
run. Configure feature probes are build admission, not ROS communication,
authority, performance, debugger or multi-architecture acceptance evidence.
