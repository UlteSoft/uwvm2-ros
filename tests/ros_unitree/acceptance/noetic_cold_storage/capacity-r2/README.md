## Bounded archive proposal before separate retirement

The829MB single body exceeds the prior plan's initial512MiB logical batch.
It needs a separately reviewed, explicit **one-file1GiB maximum** streaming
batch, with at most512MiB source RSS and1MiB chunks under Root's exact current
hard64GiB/zero-swap guard. Active8GiB reserve and deadlines remain unchanged.
There is no need to materialize a second tar or compressed copy on Linux.

Root first opens the exact ordinary nlink1 file and every parent with
O_NOFOLLOW, hashes all bytes and rechecks the current named/stat identity.
It compares fresh actual bytes to the separately recorded historical expectation
without substituting old identity fields. A newly reviewed source archiver then
emits only the finite selected member plus optional retained small context, with
complete per-member metadata/byte hashes and stable source before/after proofs.

The persistent Mac destination is Root-selected and remains null here. Root
must measure actual free space and independently bound the stream, rather than
assuming the reported roughly8GB capacity guarantees fit or predicting tar
compression. The receiver verifies the entire compressed stream hash/count,
exact member names, all body hashes and metadata, then fsyncs archive and
parent directory and records its actual durable pin.

Only a separately reviewed Root retirement can then recheck the complete
now-current consumer/physical-alias closure and the exact original current pin
before unlinking that one body. It keeps the report/command/log/ledger and
parent directories, and writes a new cold-content-location sidecar without
changing old statuses or manufacturing restored inode/ctime values. Observe
actual backing/image allocation after any owned-Btrfs-only free-block barrier.

This small finite proposal can help measured capacity. It does not establish
room for a full LLVM23 build, eight architecture SDKs or a distribution matrix;
those jobs retain their own actual serial storage/RSS/transient admission.
